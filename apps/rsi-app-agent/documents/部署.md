# 部署

平台有两种跑法，由配置决定，代码相同。

| | 单实例（默认） | 多实例 |
|---|---|---|
| 平台数据（用户、授权、版本、单据、评测、会话） | `<home>/.rsi/` 下的文件 | PostgreSQL |
| 文件（应用目录、材料、版本内容、AI 编码工作区） | 本机，或 MinIO | MinIO |
| 后台任务（单据、评测、AI 编码回合） | 本进程里执行 | Redis Streams，任一实例领取 |
| 实例之间的通知（应用变了、取消回合） | 不需要 | Redis 发布订阅 |
| 应用自己的数据库、缓存、文件、队列 | 不开通，应用自己配 | 平台按应用开通（可选） |

什么都不配就是单实例 + 本机文件，和以前一样。

## 配置

开关都是环境变量，也可以写进 `rsi.config.json` 的 `database`、`queue`、`storage`、`apps.provision`。密钥只认环境变量。

| 变量 | 含义 |
|---|---|
| `RSI_DATABASE=postgres`、`RSI_DATABASE_URL` | 平台数据进 PostgreSQL |
| `RSI_QUEUE=redis`、`RSI_REDIS_URL`、`RSI_REDIS_PREFIX`（默认 `rsi:`） | 后台任务进 Redis Streams |
| `RSI_STORAGE=minio`、`RSI_S3_ENDPOINT`、`RSI_S3_BUCKET`、`RSI_S3_ACCESS_KEY`、`RSI_S3_SECRET_KEY` | 文件进 MinIO |
| `RSI_APP_PROVISION=1` | 给应用开通 PostgreSQL、Redis、MinIO（需要上面三项，且账号有建库、建用户的权限） |
| `RSI_APP_PG_URL`、`RSI_APP_REDIS_URL` | 应用资源用另一套服务时填，不填就用平台的 |
| `RSI_WORKERS` | 每个实例同时领几个后台任务（默认 4，0 表示只接请求不干活） |
| `RSI_ENV_FILE` | 从这个文件读上面这些变量（相对平台目录）；也可写在 `rsi.config.json` 的 `envFile`。已经在进程环境里的变量优先 |

## 用 Docker 起 PostgreSQL、Redis、MinIO

```bash
cd apps/rsi-app-agent
node console/bin/cluster-env.ts          # 生成 deploy/.env：随机密码，权限 0600，不进 git
docker compose -f deploy/docker-compose.yml up -d
```

端口只绑 127.0.0.1：PostgreSQL 5432，Redis 6380，MinIO 9100（控制台 9101）。被占用时改 `deploy/.env` 里的 `RSI_*_PORT` 和对应的地址。镜像拉不到时用 `RSI_PG_IMAGE`、`RSI_REDIS_IMAGE`、`RSI_MINIO_IMAGE` 换成镜像站的。

注意 `docker compose` 优先用当前终端里已有的同名变量：终端里留着别的 `RSI_S3_SECRET_KEY` 等值时，容器拿到的是那个值，平台连不上（MinIO 报 `InvalidAccessKeyId`）。在干净的终端里执行，或先 `unset` 这些变量。

然后让平台读这个文件：在 `rsi.config.json` 写 `"envFile": "deploy/.env"`，或启动时给 `RSI_ENV_FILE=deploy/.env`。

## 把单实例的数据搬过去

```bash
RSI_ENV_FILE=deploy/.env node console/bin/migrate.ts --home <home> --dry-run   # 先看会搬什么
RSI_ENV_FILE=deploy/.env node console/bin/migrate.ts --home <home>
```

搬的是：内核数据（版本、提案、信号、单据、评测）、版本内容、用户和授权、密码、会话签名密钥、AI 编码会话和工作区、home 里的应用文件和材料。目标库里已有的数据不覆盖，要覆盖加 `--overwrite`。原来的文件不动，搬完可以回到单实例。

## 起多个实例

```bash
RSI_ENV_FILE=deploy/.env RSI_HOME=/srv/rsi/a node console/bin/serve.ts --port 8780
RSI_ENV_FILE=deploy/.env RSI_HOME=/srv/rsi/b node console/bin/serve.ts --port 8781
```

每个实例一个自己的 home（工作副本和缓存），启动时从 MinIO 取回应用。前面放一个负载均衡即可：登录 cookie 用存在数据库里的同一把密钥签名，哪个实例都认，不需要粘性会话。界面开发时用的 `next dev`（`console/web`）同样读这些配置。

## 应用的资源

打开 `RSI_APP_PROVISION=1` 后，应用的 web 进程启动时平台给它开通（已有就复用），并注入这些环境变量：

| 变量 | 内容 |
|---|---|
| `DATABASE_URL` | 应用自己的 PostgreSQL 库（`app_<应用>`，开发环境 `app_<应用>_dev`），角色只拥有这个库 |
| `REDIS_URL`、`REDIS_PREFIX`、`QUEUE_PREFIX` | Redis 用户只能读写 `rsiapp:<应用>:<环境>:` 开头的键和流，不能执行管理命令 |
| `S3_ENDPOINT`、`S3_REGION`、`S3_BUCKET`、`S3_ACCESS_KEY`、`S3_SECRET_KEY` | 桶 `rsi-app-<应用>`（开发环境加 `-dev`），用户只能访问这个桶 |
| `RSI_APP_ENV` | `prod` 或 `dev` |

连接信息不写进 `web/.env`，也不进版本和导出的压缩包：同一个版本在开发、正式环境和别的部署里拿到的是各自的资源。应用模板的 `lib/server/db.ts`、`redis.ts`、`storage.ts`、`queue.ts` 直接读这些变量；`GET /api/apps/<应用>/infra` 给管理者看开通了什么（不含密码）。

应用也会跑多份，所以：数据放数据库，文件放桶，后台任务放队列，不要放内存或本地磁盘；表结构变更用 `migrate()`（带锁，多份同时启动只执行一次）。

## 限制

- 预览（发布前试用）生成的临时文件在跑它的那个实例本地。
- AI 编码回合换到另一台机器继续时，harness 的对话记忆从新开始，平台会把之前的对话作为上下文带上。
- 文件同步以 MinIO 为准：实例停机期间别处删掉的文件，启动时本地也会删掉。
