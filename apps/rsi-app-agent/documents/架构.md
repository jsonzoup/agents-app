# 架构

> 展开[原则](原则.md)第 2、3 节。规则以原则为准。

## 目录与依赖方向

平台 `rsi-app-agent` 在工作区根目录 `apps/` 下；应用不在平台里，在 home 目录里。

```
deepseek-harness/                 内核态（上游）
└── apps/rsi-app-agent/           平台（本工程，只有 Node / TypeScript）
    ├── rsi-kernel/               自进化内核，零依赖                       （不依赖任何人）
    ├── rsi-harness/              驱动：把 rsi-kernel 的端口接到 harness 上  ──依赖──▶ rsi-kernel、harness
    ├── console/core/             平台用例：权限、应用发现与创建、业务单据、HTTP  ──依赖──▶ rsi-kernel
    ├── console/web/              平台界面：Next.js + React + shadcn/ui；/apps/... 反向代理到各应用版本的 web 应用
    ├── builder/                  AI 编码助手的定义：AGENTS.md（约定）、技能（应用包规范、评测用例）、MCP 工具（检查、测试、请用户上传）
    └── rsi.config.json           { "home": … }；环境变量 RSI_HOME 优先，都没有就用 ~/.rsi-app-agent

<home>/                           例：baoguandan-agent/testhome
├── .rsi/                         平台状态：store/（内核）、console/（用户、用户组、角色、应用授权、产物、会话密钥）、builder/（AI 编码会话）、uploads/
├── customs-declaration/
│   ├── code/                     应用本身：版本只快照它，进化只改它
│   └── evals/                    评测集（rsi-eval/1）：用例文件夹（输入材料、期望、规则）、验证程序、自测：不进版本
└── notes-digest/                 工程对照应用：证明内核不懂行业
```

home 里有 `code/app.json` 的文件夹就是一个应用，平台启动时逐个安装；装不上的报出原因，不影响别的应用。

测试守住边界：`rsi-kernel/src` 出现报关词汇或 harness 词汇（`deepseek`、`cordis`、`ctx.`、`mcp__`、`SessionEvent`……）即失败；`rsi-harness/src` 出现报关词汇即失败；`console/core` 和 `console/web/src` 出现行业词汇即失败。

## 平台 console

| 部分 | 文件 | 做什么 |
|---|---|---|
| 权限 | `core/rbac.ts` | 用户、用户组、角色（系统权限）；应用授权只分使用 / 管理，授给用户或用户组；代码级批准人数的策略（默认两位，可设为一位）；批准时一人不签两次、每个应用至少一位管理者。纯函数；策略存在 `policies.json` |
| home | `core/home.ts` | 解析 home 目录、列出其中的应用 |
| 存储 | `core/storage.ts` | 默认本机文件。`minio` 时桶是存放处，home 是执行器和裁判的工作副本，启动时按上次同步的清单双向同步（别处删掉的本地删除，本地删掉的桶里删除）；整个目录推送时桶里多出的对象一并删除，`.next` 等构建产物不上传。AI 编码的工作区按修订号镜像（`DirMirror`）。密钥只来自环境变量 |
| 部署 | `core/cluster.ts`、`core/pg.ts`、`core/pgstore.ts`、`core/redis.ts` | 单实例（默认）：文件库、任务进程内执行。多实例：数据在 PostgreSQL（`rsi_docs` 一张表存所有文档，内核计数和互斥用 advisory lock），文件在 MinIO，后台任务（单据、评测、AI 编码回合）进 Redis Streams 由任一实例领取，实例之间用 Redis 发布订阅通知应用变化和取消回合。见 [部署](部署.md) |
| 应用资源 | `core/appinfra.ts` | 打开 `RSI_APP_PROVISION=1` 后，平台给每个应用的开发和正式环境各开一套：PostgreSQL 库和角色、Redis 用户（只能用自己的键前缀）、MinIO 桶和只能访问这个桶的用户；连接信息在启动应用进程时作为环境变量注入，不写进版本 |
| 用例 | `core/console.ts` | 应用列表与摘要、代码树与差异、手动 / AI 提案、验证、批准、版本、回滚、导入人工变更；用户 / 用户组 / 角色 / 应用授权；业务单据：新建并运行、按版本试用、修正、对区域或整单提建议（信号带上整张单据的上下文）、确认、应用动作、本人修正的去向 |
| 评测 | `core/bench.ts` | 评测集文件库（[评测规范](评测规范.md)）：用例、材料、验证程序、自测的查看与修改，每次保存一个快照 `eN`；对任一版本（含候选版本 `P-N`）在后台跑全部或所选用例，结果按版本和用例呈现，每个用例有历次结果，每次评测可导出报告 `rsi-eval-report/1` |
| AI 编码 | `core/builder.ts`、`core/workspace.ts` | 会话：工作区（新应用从骨架，已有应用从稳定版）、每条消息是同一 harness 会话的一个回合、事件流式记录；检查、测试、发布。文本和二进制（表格、文档、图片）都能进提案：二进制是整体放入，删除是删除。助手的工具经本机回环通道（每个会话一个令牌，`RSI_BUILDER_BRIDGE` / `RSI_BUILDER_TOKEN`）以发起人的身份跑测试；助手请用户上传的文件记在会话旁的 `requests.json`，界面上显示为上传卡片。评测用例的改动和会话开始时的评测集快照比对，发布时由发布人确认保存，别人中途改过的文件报冲突 |
| 预览 | `core/preview.ts`、`core/actions.ts` | 发布前试用会话做出的应用：界面由工作区 `code/` 现编（`/api/builds/<id>/preview/ui.js|css`，按界面文件指纹缓存），单据在临时内核里跑（工作区装进去，文件变了才重装），存在会话目录的 `preview/`，不进工作区、不成为信号。动作执行和正式单据共用 `actions.ts` |
| 脚手架 | `core/scaffold.ts` | 新应用的骨架与标识校验 |
| 执行器 | `core/executor.ts` | 找 harness（`RSI_DSH_COMMAND`，否则本仓库 `apps/cli/lib/bin.js`）；所有单据和评测都走 harness，任务里的材料路径换成绝对路径交给智能体；每次运行按 `runConfinement` 隔离：home 里只有所跑版本目录和本次材料可读，用户目录里只有版本目录和工具缓存可写；找不到 harness 就如实失败 |
| 接口 | `core/http.ts` | Web `Request` → `Response`，任何宿主都能转发；会话是签名 cookie |
| 组装 | `core/boot.ts` | 执行器、模型（`DEEPSEEK_API_KEY`）、裁判、应用自测、AI 编码；新应用安装后回调宿主（Next 里用来重新登记应用界面） |
| 界面 | `web/` | 路由处理器把请求原样转给 `core/http.ts`（原生加载，不打包内核）；`src/sdk` 是应用界面的契约；`/apps/[...path]` 也交给 `core/http.ts`，由 `core/webhost.ts` 按版本构建、运行、代理各应用的 web 应用 |

单实例时平台状态在 `<home>/.rsi/`；多实例时在 PostgreSQL，`<home>/.rsi/cache` 只是本机缓存。用户能读的文件是：上传的材料、各应用评测材料、以及有权限时的代码包和评测集文件。平台状态本身读不到。

应用的 web 应用在版本里，是独立的 Next.js 项目：平台按 `(应用, 版本)` 安装依赖（按锁文件缓存）、`next build`、在回环端口 `next start`，使用页用 iframe 嵌入 `/apps/<应用>/v/<版本>/`。代理先做登录和权限检查，再带上调用人；应用进程拿不到平台的环境变量。清单把 `web/**` 声明为代码后，web 应用走提案和批准；只改 web 应用的提案，改进闸门直接通过。

## rsi-kernel 内部的洋葱

| 环 | 目录 | 内容 | 允许做 |
|---|---|---|---|
| 领域 | `src/domain/` | 清单与分级（`manifest`）、变更与锚点（`change`）、版本与指针（`release`）、信号与问题归并（`signal`）、评测比较（`evaluation`）、提案与批准规则（`proposal`） | 纯函数，无 I/O、无时钟 |
| 端口 | `src/ports.ts` | `AppSource`（代码树 + 评测树）、`Store`、`Executor`、`Judge`、`Learner`、`Model`、`AppTests`、`Clock` | 只有类型 |
| 用例 | `src/application/kernel.ts` | `RsiKernel`：安装、运行、记信号、提案、验证、批准、发布、回退、评测 | 只通过端口做 I/O |
| 扩展 | `src/extensions/` | 闸门（`DEFAULT_GATES`）、提案器（`scriptedLearner`、`reflectiveLearner`） | 实现端口，可替换、可追加 |
| 适配器 | `src/adapters/` | `FsStore`、`FsAppSource`、`McpStdioClient`/`mcpJudge`、`commandAppTests` | 文件、进程、MCP |

## 进化循环

```
运行 runTask ──▶ 人校正 recordSignal ──▶ 同字段同范围归成问题 issues
   ▲                                                   │
   │                                             提案器 propose / 人 submit
回退 rollback                                          │
   │                                                   ▼
发布 = 移动稳定指针 ◀── 批准 decide ◀── 验证 verify（候选版本 × 开发集/留出集，过闸门）
```

- **版本只含 `code/`**：用例、裁判、自测都在 `evals/`，从源目录运行，候选版本改不到，执行器给智能体的目录里也没有它们。评测集自己有快照 `eN`，一次评测记下用的是哪个。
- **候选版本**：提案的变更叠加在基线上，标识是 `P-N`，打开时现算，不另存一份；没批准之前它不是稳定指针。可以试用，也可以对它跑评测。文件按内容哈希只存一份，多个版本共享没变的文件。
- **只改界面**：界面不进智能体的输入，这类提案不要求输出分数变好。
- **闸门**（默认五道）：不变量（裁判的 `check` 全过）、开发集不退步、确有改进、留出集不退步（同一基线的留出集结果复用，不重复看）、应用自测（仅代码级：在 `evals/` 里跑 `node --test tests/*.test.ts`，候选代码目录经 `RSI_APP_CODE` 传入）。
- **批准**：知识级要一位管理者；代码级默认要两位不同的管理者（宿主按应用策略把要求的角色传给内核 `decide`，可减为一位），并且应用自测通过；契约级直接拒绝。基线在验证后被别的提案移动过，批准时拒绝，要求重新验证。
- **范围**：清单的 `scopes[].from` 指明从任务输入的哪个路径读范围值（如 `input.customer.code`）。运行时内核按范围给出生效的 `AGENTS.md` 链：根目录一份，加上 `scopes/<键>/<值>/AGENTS.md`。

## 驱动 rsi-harness

| 文件 | 做什么 |
|---|---|
| `src/plugin.ts` | Cordis 插件：`name = 'rsi'`，`apply(ctx, config)` 安装应用并 `ctx.provide('rsi', kernel)` |
| `src/headless.ts` | `headlessExecutor`：在版本目录里起 `dsh --profile headless --json -`，任务从标准输入进；只认最后一个 ```json 块里的 `{"status","output"}`。每次运行生成一个 `--patch` 叠加层（`releasePatch`）：把版本的技能目录设为 `skill-filesystem` 的 `customSkillDirs`，把 `.mcp.json` 里的服务器挂成 `dsh-mcp-client` 条目——harness 只从 `.dsh/skills`、`.agents/skills` 和配置的目录发现技能，也不读 `.mcp.json`，这层翻译由驱动负责。给了 `confine` 时整个进程包在隔离里运行（见 `src/confine.ts`），机器不能隔离就不执行 |
| `src/confine.ts` | 进程级隔离：harness 自带的沙箱只限写不限读，智能体能读到用户能读的一切。现只实现 macOS Seatbelt（`sandbox-exec`）；Seatbelt 不能嵌套，所以隔离的进程关掉 harness 内层沙箱（`DSH_PERMISSION_MODE=danger-full-access`），写规则也由这层承担 |
| `src/session.ts` | 一个可续的对话回合：`dsh --profile headless --patch <叠加层> --json [--session-id <id>] -`，事件边到边转给调用方。AI 编码助手用它：叠加层挂上 `builder/skills` 和 `builder/mcp/server.ts`。启动器参数（`--profile`、`--patch`）必须在应用参数之前 |
| `src/trace.ts` | 把 headless 的 JSON 事件流和 harness 会话日志（`SessionEvent`）归一成内核的 `TraceStep` |

发布批准不用 harness 的 `ctx.approval`：那是单个智能体的工具审批，和版本发布不是一回事。

## 当前环境的限制

- harness 使用独立目录准备的兼容 CLI，通过 `RSI_DSH_COMMAND` 指定；只读子模块不安装、不构建。AI 编码助手、单据执行和评测都走真 harness（会话、技能、MCP 检查、测试）；模型配置来自 harness 自己的设置，不经过本平台。
- 没有 `DEEPSEEK_API_KEY` 时 `reflectiveLearner` 不可用，界面上直说。
- 任务输入里的材料路径相对 home；交给 harness 前由 `Console.executorInput` 换成绝对路径（文件先确保在本地）。
