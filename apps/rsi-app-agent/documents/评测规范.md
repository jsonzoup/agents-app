# 评测规范 rsi-eval/1

每个应用的 `evals/` 按这份规范组织：**一个用例一个文件夹**，里面放齐它的输入材料、期望结果、验证规则和用哪个验证程序；评测结果和报告格式统一。平台内核（`rsi-kernel`）加载和打分，平台（`console`）维护、运行、出报告，AI 编码助手按它写用例。

## 1. 目录

```
<应用>/evals/
├── eval.json                 评测集清单（可省略，省略即默认值）
├── cases/                    用例目录，名字由 app.json 的 evals.cases 决定
│   └── <id>/
│       ├── case.json         用例：输入、期望、规则、验证程序、出处
│       ├── input/            输入材料（PDF、表格、图片……），input 里按路径引用
│       ├── expected/         可选：期望结果文件（期望写成文件时）；oracle.json 是参考答案
├── judge/                    默认验证程序（app.json 的 judge 指向它）
├── validators/<名>/          可选：其他验证程序，在 eval.json 里声明
├── tests/、tools/        可选：应用自测、维护脚本
└── expect.ts                 可选：把确认过的单据结果转成期望的形状
```

`evals/` 不进版本，执行任务的智能体看不到它。它的每次改动由内核生成快照（`e1`、`e2`…），每个分数都记着用的是哪个快照。

## 2. eval.json

```json
{
  "spec": "rsi-eval/1",
  "validators": {
    "tolerant": { "command": "node", "args": ["validators/tolerant/server.ts"], "title": "数值允许误差" }
  },
  "tags": { "smoke": "冒烟：每次改动都跑", "edge": "边界情况" },
  "capabilities": { "跨单据核对": "毛重、件数等在不同单据间核对并报差异" },
  "trials": 1
}
```

- `validators`：除默认的 `judge` 之外的验证程序。`judge` 这个名字留给 `app.json` 的 `judge`。
- `tags`：标签的含义，给人挑用例时看。
- `capabilities`：能力词表，即这个应用要会的本事。用例的 `capabilities` 只能用词表里的词；体检按词表出覆盖矩阵，词表里没有用例覆盖的能力会被提示。
- `trials`：发布前验证时每个用例跑几次（1–5，默认 1），见第 7 节。

## 3. case.json

```json
{
  "id": "c1",
  "title": "一句话说明这个用例考什么",
  "tags": ["smoke"],
  "split": "dev",
  "source": "出处：谁在什么时候给的、来自哪份真实单据",
  "scope": { "customer": "acme" },
  "input": { "materials": [{ "path": "<应用>/evals/cases/c1/input/a.pdf" }] },
  "difficulty": "medium",
  "why": "难在哪里：合计要从两张发票加总，单张发票上没有",
  "capabilities": ["跨单据核对"],
  "input": { "materials": [{ "path": "<应用>/evals/cases/c1/input/a.pdf" }] },
  "expected": { "total": "120.00" },
  "oracle": "expected/oracle.json",
  "rules": [
    { "path": "status", "op": "equals", "value": "result" },
    { "path": "output.total", "op": "number", "value": 120, "tolerance": 0.01 }
  ],
  "validator": "judge"
}
```

| 字段 | 必填 | 含义 |
|---|---|---|
| `id` | 是 | 和文件夹同名 |
| `title` | 是 | 用例考什么 |
| `input` | 是 | 任务输入，必须满足输入契约；材料路径相对平台 home，写成 `<应用>/evals/cases/<id>/input/<文件>` |
| `expected` | 二选一 | 期望结果：直接写对象，或写成用例文件夹里 `.json` 文件的相对路径（如 `"expected/result.json"`）。形状由验证程序决定 |
| `rules` | 二选一 | 声明式验证规则，见第 4 节 |
| `validator` | 否 | 验证程序名。有 `expected` 时默认 `judge`；写 `null` 表示只用规则 |
| `split` | 否 | `dev`（默认）或 `holdout`；也可以在 `app.json` 的 `evals.holdout` 列出 |
| `tags` | 否 | 标签，用来挑用例批量跑 |
| `source` | 建议 | 期望值和材料的出处。期望值只能来自真实材料和人给出的值 |
| `scope` | 否 | 执行时的范围（如某个客户），对应 `app.json` 的 `scopes` |
| `difficulty` | 建议 | `easy` / `medium` / `hard`。评测集要有难度梯度，全是 easy 会被提示 |
| `why` | 建议 | 这个用例难在哪里、为什么值得考 |
| `capabilities` | 建议 | 考哪些能力，只能用 `eval.json` 词表里的词 |
| `oracle` | 建议 | 参考答案：`{status, output, provenance}` 对象，或用例文件夹里的文件路径（通常 `expected/oracle.json`）。见 3.1 |

`expected` 和 `rules` 至少有一个；有验证程序就必须有 `expected`。内核加载时逐条检查，不合规的用例会报出问题，并且不参与评测。

`"expected": {}` 且没有规则的用例是**待确认**的：材料齐了，期望值还没定。在编码工作区里，助手在这个用例上真实运行应用，把结果拿给人确认；人确认，或改正不对的值后，平台把结果按“输出路径 → 值”写进 `expected`（如 `{"items[0].name": "…"}`），`source` 记下谁在哪天确认的。待确认的用例测试时跳过，有待确认的用例就不能发布。

### 3.1 参考答案（oracle）

参考答案是这个用例的一份**已知正确的完整执行结果** `{status, output, provenance}`。`provenance` 写明它从哪来：

- `confirmed-run`：人在编码工作区确认（或改正）了一次真实运行，平台写入，同时写 `expected`；
- `confirmed-task`：从人确认过的单据生成用例时带上；
- 其他，如 `acceptance-replay`：技能作者写在验收测试里、经真实运行器规范化的阶段输出，记录测试名和文件哈希。

参考答案只能由平台或人写入，编码助手不能写，也不能用模型现场跑出来的结果冒充。

**自检**：每次评测前，内核先用这个用例的规则和验证程序给参考答案打分。参考答案没得满分（或有违例）说明期望值、规则或验证程序本身错了，这时用例记为**无效**，不执行、不计分，报告和“评测完整”门禁会指出来。没有参考答案的用例照常评测，体检提示“无法证明期望值和裁判对正确答案给满分”。

## 4. 声明式规则

每条规则从执行结果 `{status, output}` 里按路径取一个值来检查，一条规则就是一个检查项。

路径写法：`status`、`output.title`、`output.rows[0].price`、`output.items[name=重量].value`（数组里 `name` 等于“重量”的第一项）。

| op | 参数 | 通过条件 |
|---|---|---|
| `equals` | `value` | 等于（按文本比） |
| `number` | `value`，`tolerance` 或 `relative` | 数值差不超过绝对误差或相对误差 |
| `oneOf` | `values` | 是其中之一 |
| `contains` | `value` | 文本包含，或数组含有该项 |
| `matches` | `pattern` | 匹配正则 |
| `count` | `value` 或 `min`/`max` | 数组长度 |
| `present` / `absent` | — | 非空 / 为空 |

可选的 `label` 用来在报告里代替路径显示。

## 5. 验证程序

验证程序是一个 MCP stdio 服务，工作目录是 `evals/`，只给内核用。两个工具：

- `score({case, run})` 返回 `{checks: [{path, ok, expected, actual}]}`，逐项比对。`case` 是解析后的用例（`expected` 已从文件读出），`run` 是 `{status, output, trace}`。
- `check({run})` 返回 `{violations: string[]}`，即硬规则。任何违例都会挡住发布。

规则做不到的比对（跨字段核对、按业务口径归一化）才写成验证程序。一个应用可以有多个，用例用 `validator` 选。

## 6. 打分

一个用例的检查项是规则的检查项加上验证程序的检查项。得分为通过的检查项数除以总数；全部通过且没有违例，用例才算通过。分数按“执行内容 + 用例内容 + 验证程序内容 + 执行器”缓存，只改一个用例就只重跑这一个。

**执行出错不算答错。** 一次运行有三种结局：

| 结局 | 含义 | 计分 |
|---|---|---|
| 正常打分 | 智能体给出了结果（包括它自己答错、超时、用完预算） | 计入通过数、总数和得分 |
| 出错 `error` | 不是智能体的问题：没有可用的执行器、隔离环境起不来、进程异常退出且没有任何回答 | 不计分，不缓存，下次重跑 |
| 无效 `invalid` | 参考答案没得满分，用例本身有问题 | 不执行，不计分 |

执行器在 `RunResult.error` 里说明出错原因。集合汇总的 `total` 和 `score` 只算正常打分的用例，`errors`、`invalid` 单列。比较两个版本时跳过任一边出错或无效的用例（记在 `skipped`），不会把基础设施故障算成退步。

**多次运行。** 跑 k 次（`trials`，1–5）时每次单独缓存，按通过率汇总：

- 检查项通过率 `rate` 超过一半算通过；用例通过率 `passRate` 超过一半算通过；
- 违例取所有次的并集；出错的那几次不参与汇总，全部出错才算这个用例出错；
- 比较版本时，**稳定退步**（基线每次都过、候选过半失败）才算退步，**稳定修复**同理；介于两者之间的检查项记为不稳定 `unstable`，在报告和门禁里提示，不挡发布。

## 7. 运行

- **全部**：按开发集、留出集跑一个版本（已发布版本或提案的候选版本），是发布判断的依据。
- **所选用例**：在“评测”里勾选多个用例（可按标签筛选）后运行。结果标为“部分用例”，**不作为发布依据**。
- 运行在后台进行，逐个用例报告进度；服务重启时未完成的运行记为失败。
- **跑几次**：发起运行时可选 1–5 次；发布前验证按 `eval.json` 的 `trials`。
- **消融**：发起运行时可选“去掉知识”（只留 `agent.instructions` 和各技能的 `SKILL.md`，去掉规则、参考资料等知识层文件）或“去掉技能”（去掉全部技能目录）。消融运行和同一版本、同一评测集快照上最近一次完整运行逐个用例对比，看出知识和技能各贡献了多少。消融结果不进版本成绩，也不作为发布依据。
- **评测完整门禁**：发布前验证里任何集合有出错或无效的用例，“评测完整”门禁不通过，先修好环境或用例再验证。

## 7.1 用例体检

`GET /api/apps/<应用>/bench/audit`，编码工作区的检查也会跑同样的体检。逐个用例检查：

- 参考答案能否得满分（不能就是问题）；没有参考答案（提示）；
- 期望值是否待确认；`source`、`difficulty`、`why`、`capabilities` 是否缺；
- `capabilities` 是否都在词表里（不在就是问题）；
- `input` 引用的材料是否存在、`sha256` 是否和文件一致（不一致就是问题）。

整个评测集再看：词表里没有用例覆盖的能力、没有留出集、全部是 easy。体检同时给出**能力覆盖矩阵**：每个能力有几个用例、几个计了分、几个通过（用最近一次完整的稳定版本运行）。

## 8. 结果与报告

运行记录保存在平台的状态库里，按用例分组展示；每个用例可以看到它在历次运行中的结果。每次运行可以导出标准报告：

- JSON：`format: "rsi-eval-report/1"`，含应用、版本、评测集快照、执行器、发起人、起止时间、所选用例、各集合汇总（通过数、总数、得分、出错数、无效数），以及每个用例的检查项、违例、状态、耗时和输出；出错或无效的用例带原因。跑了多次的还有 `trials`、每个用例的 `passRate` 和逐次结果；消融运行有 `ablate` 和与完整运行的对比 `ablation`；另有能力覆盖 `coverage`。
- Markdown：同样内容的可读版本，只列没通过的检查项；出错标 ⚠️、无效标 🚫，并有“消融对比”“能力覆盖”两节。

接口：`GET /api/apps/<应用>/bench/runs/<运行>/report?format=json|md`，加 `&download` 表示下载。

## 9. 兼容

旧布局（材料放在 `evals/materials/<id>/`、录制放在 `evals/replays/`）已迁移到用例文件夹。历史单据和信号里的旧材料路径 `<应用>/evals/materials/<id>/<文件>`，在旧文件不存在时由平台映射到 `<应用>/evals/cases/<id>/input/<文件>`。
