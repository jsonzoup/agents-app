# 原则

> 2026-10-09 起生效。本仓库实现报关单 Demo 时，这是唯一的指导。其他文档只展开它，不另立规则；与它冲突的以它为准。

## 1. 我们在造什么

一个让垂直业务智能体**自己变好**的底座。报关单是第一个试点，不是终点：同一个底座要能长出别的行业的智能应用，每个应用都在真实使用中积累反馈，经验证、经人批准后变成新版本。

## 2. 三层，用操作系统来类比

| 层 | 类比 | 是什么 | 例子 |
|---|---|---|---|
| **deepseek-harness** | 内核态 | 让一个智能体真正跑起来：模型调用、工具流水线、技能加载、MCP、会话日志、沙箱、审批、Web 外壳。它本身由很多 Cordis 插件组成。 | `ctx.agents`、`ctx.tools`、`ctx.skills`、`ctx.agentPresets`、`ctx.sessionQuery` |
| **rsi-kernel** | 系统内核 / 驱动框架 | 面向自进化的通用内核：管理应用的版本、收集信号、提出变更、验证、发布、回退。它不懂任何行业，本身也靠扩展长能力。 | 信号、提案、验证、发布、谱系 |
| **垂直应用** | 用户态程序 | 一个行业的智能体：知识、技能、少量确定性代码、评测用例、契约。住在 home 目录里，不在平台源码里。 | `<home>/customs-declaration` |

运行时，rsi-kernel 作为 harness 的插件装进同一个进程，就像驱动装进内核。源码上，rsi-kernel 的核心一行也不 import harness：harness 那一侧由一个很薄的驱动包 `rsi-harness` 去适配。这一点和真实操作系统一样：内核定义驱动接口，具体硬件的驱动去实现它。

三层之上是**平台**（`console/`），相当于操作系统的桌面与系统设置：登录与权限、应用登记与创建、业务单据、把人的修正变成信号、把内核的版本 / 提案 / 评测摆给人看。它是最外层的适配器，只调用 rsi-kernel 的用例，同样不懂任何行业；每个应用自己的业务界面由应用提供，平台只负责挂载。

## 3. 依赖规则

参考六边形架构、洋葱架构、DDD 和整洁架构，落成下面五条。

1. **源码依赖只向内。** 越靠里越稳定、越抽象。应用依赖 rsi-kernel 的契约；`rsi-harness` 依赖 rsi-kernel 的端口和 harness 的服务；rsi-kernel 不依赖二者中的任何一个。
2. **边界接口由稳定的一侧拥有。** rsi-kernel 拥有两组接口：向下的**端口**（执行器、存储、模型、人工、裁判……），由驱动实现；向上的**应用包规范**，由每个应用实现。harness 拥有自己的 Cordis 服务接口，只有 `rsi-harness` 去碰它。
3. **每一层内部也是洋葱。** 中心是领域模型（实体与规则，纯函数，无 I/O）；外面是用例（编排领域对象、调用端口）；再外面是适配器（文件、进程、MCP、harness）。领域代码不读文件、不起进程、不看时钟，这些都从端口进来。
4. **限界上下文各说各的话。** 执行上下文的词（Cordis、`ctx.*`、`mcp__`、`SessionEvent`、preset）只出现在 harness 和 `rsi-harness` 里；进化上下文的词（信号、提案、验证、发布、谱系）只出现在 rsi-kernel 和应用清单里；行业的词（表头、征免、关区、HS）只出现在那个应用里。跨上下文只传契约里定义过的数据，由清单和驱动做防腐翻译。
5. **扩展，不修改。** 每层都只在公开的扩展点上加东西：harness 加 Cordis 插件；rsi-kernel 加扩展（信号源、提案器、评分器、闸门、执行器、存储、界面）；应用加知识文件、技能、MCP 服务。改动内层来满足某个外层，说明边界画错了。

判断一处改动放在哪一层，按顺序问：

| 问题 | 是 → 放在 |
|---|---|
| 换一个行业也成立吗？不成立 | 那个应用 |
| 换一个执行器（不是 harness）也成立吗？不成立 | `rsi-harness` 驱动 |
| 与“怎样让应用变好”无关、只与“怎样让智能体跑起来”有关？ | harness（提给上游，不在本仓库改） |
| 其余 | rsi-kernel；先找现有扩展点，没有再加端口 |

## 4. 应用是什么

平台有一个 **home 目录**（可配置）。home 下每个应用一个文件夹，平台自己的状态在 `.rsi/`。平台源码里不放任何应用。

一个应用文件夹分两半：

- **`code/`：应用本身**，由公开约定拼成，不发明新格式。版本只给它拍快照，进化只在它里面改。
  - `AGENTS.md`：给智能体的总说明，按 [agents.md](https://agents.md/) 约定。离任务最近的一份生效，所以客户等范围知识写成子目录里的 `AGENTS.md`。
  - `skills/`：怎么做，按 Agent Skills 约定（`SKILL.md` + `references/` + `scripts/`）。技能是应用的一部分，拷贝进来，不链接到别处。
  - `.mcp.json`：接哪些外部系统，按 MCP 的标准服务器配置。数据库、对象存储、业务系统都是 MCP 服务器；入参和返回值就是 MCP 的 `inputSchema`、`CallToolResult`。密钥只以环境变量进入。
  - `app.json`：给 rsi-kernel 看的清单：任务输入输出契约、范围从输入的哪里读、哪些文件允许进化、评测怎么跑、业务界面和动作。
  - `contract/`：输入输出契约。`web/`：应用自己的 web 应用（全栈 Next.js，带自己的 `.env`），随版本发布，平台按版本构建运行、嵌在使用页里；处理任务的智能体看不到它。
- **`evals/`：怎么评判它**，按[评测规范](评测规范.md) `rsi-eval/1`：一个用例一个文件夹，里面是输入、输入材料、人工期望、声明式验证规则和所用的验证程序；另有验证程序（裁判）和应用自测。它永远不进入应用版本，进化改不到；智能体运行在进程隔离里，只能读到所跑版本和本次材料，看不到评测集；人在评测页维护这套文件（AI 编码助手起草的改动由发布的人确认），每次保存生成一个评测集快照，评测结果记下用的是哪一个，并能导出标准报告。

应用对内核暴露的代码能力（裁判）也走 MCP；裁判只对内核可见，不对智能体可见。

应用相关文件默认放在本机 home 目录。也可以改成 MinIO（或兼容 S3 的存储）：桶是存放处，home 是执行器和裁判用的本地工作副本，启动时同步。元数据（版本、提案、信号、单据、用户）仍在 home 的 JSON 状态里。

## 5. 自进化的边界

**进化只能改提案者够得着的东西，而评判它的东西永远够不着。**

| 级别 | 包含 | 谁能提议 | 发布前必须 |
|---|---|---|---|
| 知识 | `AGENTS.md`、`SKILL.md`、`references/`、范围知识 | 进化循环、人 | 开发集不退步，留出集只看一次，不变量全过，一位管理者批准 |
| 代码 | 技能脚本、本地 MCP 服务、清单里声明的 web 应用（通常是 `web/**`） | 进化循环、人 | 上面全部，再加应用自测通过、管理者批准（默认两位，应用可设为一位）。只改 web 应用的提案不要求输出变好：web 应用不进智能体，以不退步和人的批准为准 |
| 契约 | `app.json`、`.mcp.json`、`contract/`，以及清单没有声明为知识或代码的一切文件 | 只有人 | 不走进化循环，按普通代码评审 |

`evals/` 不在这张表里：它根本不进应用版本，只由人改，改动记成评测集快照。哪些文件属于知识、哪些属于代码，由清单的 `evolve` 声明；没声明的默认是契约。`app.json`、`.mcp.json`、`contract/**` 永远是契约，划进可进化范围时内核加载即报错；提案碰到契约文件，提交时直接驳回。rsi-kernel 自己永远不在任何应用的可写范围里。期望值只由人改；进化的工作是让新版本追上期望，而不是改期望去迁就版本。

## 6. 证据与可回退

- **每次运行可重建。** 输入、所用版本、会话日志、输出都留下；harness 的“模型可见即已记录”是这一条的地基。
- **每次进化有决策记录。** 格式就是业务方已经在用的决策记录：背景、候选方案、决策、影响与复查条件。没有记录的变更不能发布。
- **发布是移动指针。** 版本不可变；回退就是把指针挪回去。已发布的是 `rN`，提案先成为候选版本 `P-N`（基线加上改动），批准后才生成新的 `rN` 并移动指针。正在办的任务留在它开始时的版本上。
- **人在关键处。** 风险暂停、契约变更、发布批准都由人做。人的反馈记成信号，并当场说明适用范围：只这一票、这个范围、所有任务。反馈不必是单个字段：可以改一个值，也可以对一块区域或整张单据提改进建议；还可以对应用本身提建议——界面哪里不好用、缺什么功能，这类建议不分范围，不需要单据，交给编码助手改应用的代码。信号带上当时整张单据的输入、应用输出和已有修正，改进的人看到的是提出时的完整上下文。“只这一票”不进入学习。

## 7. 数据只用真的

只用真实材料和真实期望值：A–D 四票材料拷贝自 customs-extraction-skill 仓库的 `tests/fixtures`，放在报关应用各用例文件夹的 `input/` 里（`evals/cases/<id>/input/`），期望值只取技能验收测试里真实写着的断言。业务方提供的欧莱雅（中国）有限公司报关单只有终稿、没有材料，可作口径参照，不能做评测用例。

单据和评测一律由真实智能体执行（harness），没有模拟、回放这条路：harness 不可用时，执行如实失败并写明原因。评测分数一律由裁判程序现算，不手写。历史记录保持原样，当时用的执行器记在每次运行里。

唯一的例外是工程对照应用 `notes-digest`：它的用例是构造的，只用来证明 rsi-kernel 不依赖任何行业，名字和说明里都写明了，不能当业务证据。

## 8. 界面

- **使用、管理、系统管理是三个一级入口。** “使用”在最上面，每个能用的应用一项，点进去就是业务界面。“应用管理”列出我管理的应用，进入一个应用后用页签切换：应用包与代码、改进信号、提案、评测、版本与发布、权限；从管理页可以一键打开使用页，使用页上管理者也能一键回到管理。“系统管理”是用户、用户组、角色。看不到的不显示，没有“总览”。
- **创建应用靠对话。** 人只给名称和目标需求，AI 编码助手（跑在 harness 上，有自己的 `AGENTS.md`、技能和检查用的 MCP 服务，见 `builder/`）边对话边写应用包；人实时看文件树、看改动、可以直接改文件，检查、测试通过后发布。新应用发布为 r1；已有应用的“AI 修改”走同一个会话、同一套对话界面（在应用包页里默认折叠，展开即对话），发布出来的是提案，照常验证和批准；改到契约文件时是一次人工导入，由发布的管理者负责评审。助手改的评测用例在发布时由发布的人确认后保存，期望值仍只来自人。
- **编码助手有约定，平台来检查。** 业务界面必须植入改进入口（`EditableValue` 修正值、`SuggestButton` 提建议、`ContributionBanner` 看去向），检查不过不能发布；按评测规范为每个场景写用例；每改一批文件先检查、再用平台执行器真实测试并报告结果；缺真实材料时不编造，在对话里出一张上传卡片请人提供；期望值不让人上传或手填，而是助手在用例上真实运行，把结果拿给人确认“是不是你期望的”，人确认或改正后由平台写成期望值，人只说哪里不对时助手改应用再请他确认。
- **业务界面由应用自己做，并且随版本进化。** 每种业务有自己的流程和布局：报关是“单据列表 → 新建（上传材料、选业务类型和客户）→ 对照原件审核 → 确认 → 生成草单”。应用在 `web/` 里提供自己的 web 应用——页面和服务端（数据库、外部接口、大模型、对象存储）都在里面——用平台的组件库和宿主接口（`HostApi`），平台不写死任何行业字段；平台按所看版本构建运行，所以试用一个候选版本时，看到的界面和处理逻辑都是那个版本的。没有界面的应用用平台的通用任务视图。
- **看文件要能看懂。** 代码包、评测集和工作区里的 Markdown 可以预览也可以看源码；代码文件用编辑器展示并带补全；表格、文档、演示文稿、图片、音视频可以预览或播放。这些文件都可以上传进代码包或评测集。
- **普通用户无感参与进化。** 办业务时可以改一个值，也可以对一块区域或整张单据提改进建议，并选范围：只这一票 / 这个范围 / 所有单据。对界面和功能的意见随时可提：每个应用页顶部都有平台自己的“提建议”，不依赖应用自己的页面，所在页面会一起记下，截图可以直接粘贴。“只这一票”不进入学习；其余成为信号，归成问题，连同当时整张单据交给应用的管理者。管理者可以不采纳并写明原因，提出的人在应用里看得到。修正的去向（已入队、已起草、已随 rN 发布、不采纳）回到业务界面上告诉本人，不需要他去别处看。
- **评测是给某个版本出的卷子。** 评测集由人维护：用例（各带材料、期望、规则）、验证程序、自测。任何版本，包括还没发布的候选版本，都可以拿来评测；开发出一个新版本后，先试用、再对这个版本跑评测，通过验证和批准后才成为稳定版。也可以勾选几个用例只跑它们，用来看问题，不作为发布依据。分数只由规则和验证程序计算，每次评测都有标准报告。
- **新版本先试用再上线。** 候选版本可以在使用页试用，也可以在评测页对它跑评测集。试用单据单独存放，只有管理者看得到，不进入改进信号。
- **两种修正，同一条路。** AI 修正（从问题或一句话开一个 AI 编码会话）和手动修正（在应用包里改文件、写决策记录）产出同样的提案，过同样的验证和批准。
- **每个值都能追到依据。** 字段名上停留看 `reason`；风险标在它影响的字段上；原件和结果并排。
- **不装作有能力。** 未接入的 harness、未配置的模型，都在界面上直说，按钮给出原因而不是假装成功。

## 9. 权限

- **应用只分两种权限：使用、管理。** 使用：办理业务、修正结果、提改进建议。管理：在使用之上，看应用包、维护评测集、写和验证提案、批准发布、回滚、跑评测、试用未发布的版本、给别人授权。授权对象是用户或用户组；一个人的权限取他所有授权里最高的一级。
- **系统权限靠角色。** 角色是一组系统权限：管理用户与用户组、管理角色、创建应用、管理所有应用。内置“系统管理员”（全部）和“应用开发者”（创建应用），可以自定义角色。创建者自动获得新应用的管理权。
- **服务端检查每个请求。** 界面只是藏起没权限的入口；越权请求返回 403。
- **发布要管理者批准，代码级默认两位。** 知识级一位管理者批准；代码级默认两位不同的管理者批准，一人不签两次。每个应用的管理者可以在“权限”里把代码级改为一位，改动记下谁、何时改的，提案页显示当前规则；契约级不经提案发布，不受这个设置影响。每个应用至少一位可用的管理者（不算“管理所有应用”的系统权限）。
- **账号与密码。** 本地账号用密码登录，只存加盐哈希；系统管理员新建用户时设初始密码、也可重置，本人可改。改密码或重置后旧会话失效。接入企业单点登录只换服务端的登录与身份识别，权限模型不变。
